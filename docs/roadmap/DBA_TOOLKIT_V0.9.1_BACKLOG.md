# DBA Toolkit V0.9.1 Backlog — Single Task Status Ledger

## 1. Authority and update rule

This file is the only authoritative source for task and bug status. Roadmap defines direction, Progress points to the current and next IDs, and Acceptance records evidence; none of those files independently changes a task state.

Every state change must update `updated_at`, cite the evidence or decision that caused it, and preserve the Task ID. An umbrella task may have child tasks, but two active IDs must never describe identical work. Historical IDs that now map to a canonical task are aliases and have no independent state.

## 2. Status model

| Status | Entry condition | Exit condition |
|---|---|---|
| `TODO` | Approved, scoped work has not started. | Work begins or is deliberately deferred. |
| `IN_PROGRESS` | The user authorized the task and work is active. | Code/docs complete, blocked, or returned to TODO by user decision. |
| `BLOCKED` | Work cannot progress without an identified external condition or user decision. | Blocker is removed and user authorizes resumption. |
| `CODE_COMPLETE` | Required implementation/docs are complete and local review gates pass; real E2E is not required or not yet run. | E2E is required (`E2E_PENDING`) or acceptance is verified. |
| `E2E_PENDING` | Implementation exists, but required current-HEAD real E2E is absent or incomplete. | Scoped E2E passes (`VERIFIED`) or exposes more work. |
| `VERIFIED` | The task's defined evidence and acceptance criteria pass within an explicit scope. | User accepts closure (`DONE`) or later evidence reopens it. |
| `DONE` | User-accepted task closure; future changes use a new task or Bug ID. | Reopened only by explicit user decision with recorded reason. |
| `BACKLOG` | Valuable retained work is outside the current authorized sequence. | User schedules and scopes it as TODO. |
| `CANCELLED` | The user explicitly cancelled the request; retain the record and rationale, but perform no further work under this ID. | Reopen only by explicit user decision; any materially new requirement should receive a new task ID. This is not `DONE`. |

Automated tests alone cannot move a database E2E task beyond `CODE_COMPLETE`. Historical E2E cannot automatically verify the current HEAD. `DONE` does not mean every database version is verified unless that exact matrix is in the task completion criteria.
